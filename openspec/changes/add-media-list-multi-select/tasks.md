## 10. Design/spec drift to reconcile (RECONCILED — kept as historical record)

The items below were concrete mismatches between design.md's Context/Decisions
and the code as it stood on 2026-09-13. An adversarial review caught the same
issues plus additional ones (focus-loss clearing during context-menu open,
the shell-queries-component pattern in the original tasks 5.3/8.2, Queue's
unconditional Mark Played/Unplayed). All of it has since been folded into
design.md (Context, D0, D2, D7, D8, D9, Non-Goals) and this file's own tasks
1.2, 2.4/2.4a/2.4b, 3.4, 5.3, 7.1, 7.5, 7.6, 8.2, and spec.md. This section is
kept only as a record of what was wrong and caught, not as an open item.

- **D0's premise understates Slice 1's scope.** design.md claims "Today only Home and Queue open row menus via the owner's `RowIntent::Context`," implying Home/Queue are already unified and Slice 1 only "widens" one existing path. In reality, only Home's and Queue's *keyboard* `.` paths route through `RowLocalInput::Context` → `RowIntent::Context` (`src/app/components/home_content.rs:333-344`, `src/app/components/queue.rs:332-344`). Their *mouse* right-click paths bypass `RowIntent::Context` entirely and build a `ShellRequest` directly from the resolved target (`home_content.rs:478-482`, `queue.rs:420-429`), exactly like Browser/TV/Music. Home additionally uses two different `ShellRequest` variant names for the same semantic action depending on trigger — `HomeContextMenu` (keyboard) vs `HomeRowContextMenu` (mouse), `src/app/components/msg/shell.rs:173-176` vs `203-206` — a divergence design.md never mentions. Slice 1 therefore has six-plus call sites to convert (Task groups 1-2), not one to widen.
- **The named `ShellRequest` variant list is incomplete.** design.md's D0 lists six variants (`BrowserContextMenu`, `BrowserRowContextMenu`, `EmbyLibraryContextMenu`, `MusicAlbumContextMenu`, `MusicTrackContextMenu(At)`, `TvHitContextMenu`). The current tree also has `HomeContextMenu`, `HomeRowContextMenu`, `QueueContextMenu`, `QueueRowContextMenu`, and two distinct Music-track variants (`MusicTrackContextMenu` and `MusicTrackContextMenuAt`) — roughly ten variants total (`src/app/components/msg/shell.rs`).
- **The podcast bulk-action reuse precedent does not exist.** design.md's Context section states "Bulk actions already exist for podcasts (`MarkItemsPlayed(Vec<_>)`, `MarkItemsUnplayed(Vec<_>)`)." A repo-wide search (`rg -n "MarkItemsPlayed|MarkItemsUnplayed" src/`) finds zero matches. `ContextAction` (`src/app/types_context_menu.rs:21-37`) only has single-item `MarkPlayed(String)`/`MarkUnplayed(String)`. D7/D8's bulk played/unplayed actions must be designed and built from scratch (Task 7.2/7.6), not adapted from an existing pattern.
- **"Bulk effects run off the UI thread" has no existing pattern to reuse either.** `execute_context_action` (`src/app/context_menu_actions.rs:8-113`) runs every action synchronously inline on the UI thread today — e.g. `context_set_played` (line 115) locks the Emby client and calls it directly. There is no existing async/worker plumbing for context-menu actions to extend for D7's "runs off the UI thread and reports partial failure" requirement; Task 7.6 flags this as an open scoping question (build it now vs. defer to a follow-up) rather than assuming reuse.
- **`App::play_items_routed` is `EmbyItem`-typed, not generic across Services.** The one existing "replace queue with N items, start at index" entry point (`src/app/actions.rs:143`, reused for Album play) takes `Vec<EmbyItem>`. D7/D8's Play/Shuffle bulk actions for Feeds/Audiobookshelf selections (if those Services' items ever reach this path) will need either a second entry point or a shared abstraction that doesn't exist today — worth a design decision before Task 7.3 is implemented for non-Emby lists.

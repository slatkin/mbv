# Design: add-gui-library-panel

## Context

See `proposal.md` for the why and `specs/` for the requirements. The canvas reference is a verbatim local copy of the canvas files in `canvas/`: `canvas.json` (the index, with the SPEC note on multi-select pills), `Library.dc.html` (*Library — Music › Hip-Hop*), `Main.dc.html` (*Queue panel — expanded*), `Collapsed.dc.html`, and `Menus.dc.html`. The copy is a source to read; its `./support.js` runtime belongs to the canvas host. The live canvas is `https://claude.ai/artifact/D8uLGS6NyCeHd6ed7PHgsr`.

The canvas is the specification for the GUI Library panel. The GUI does not keep parity with the TUI, and the TUI does not change (ADR 0036). Where the canvas is silent, this design decides, and it says so.

What the code holds today:

- The GUI core thread (`crates/mbv-gui/src/core_thread.rs`) owns an `App`, emits `GuiWindowFrame` on `mbv://frame`, and takes `key`, `pointer`, and `report_layout` commands (`docs/architecture/gui-client.md`). The front end forwards every keydown and pointer event and interprets none (`ui/src/lib/bridge/input.ts`).
- GUI-only presentation state already lives on the `App` in `src/app/gui_client_state.rs`, and the TUI never reads it. That module is the precedent for the GUI Library's core half.
- `CoreThread::new` runs only `App::start_emby_client_fill`, an authentication-only Emby worker, and sets Queue Panel focus on its own `FocusStack`. So `App::libs` stays empty in the GUI. The TUI's Service bootstrap is `Model` code: `Model::spawn_startup_services` (the Emby and Audiobookshelf startup workers, `start_feed_fetch`, capability registration), then `Model::fetch_home_at_startup` and `Model::init_idle_feed`.
- The `App` holds the Service data of every destination: `libs` (each library's `nav_stack`), the Audiobookshelf browse states, and `feed_tab`. Home's content is the exception: the TUI shell holds it in `Model::home_content`.
- For a Grouped Music library, `nav_stack` holds the group level and the album level of one group. `App::switch_music_group` and `App::select_music_group` replace that one album level, and `App::spawn_browse` lands each fetched page in the `nav_stack` level whose parent matches. The `App` also holds `album_artist_cache` (warmed for every group by `App::spawn_music_group_warmup` when the Emby Service completes), `album_tracks_cache` (filled by `App::fetch_album_tracks`), and the card image cache (filled by `App::fetch_card_image`).
- The `App` loads the TUI launch state at construction for both Clients (`LaunchRestore::Pending`), and the restore settles `App::tab` when the catalog lands. The GUI never saves a launch state.
- `App::effective_panel_focus` and `App::effective_panel_mode` apply two TUI rules: the terminal-width Mini check (`is_mini_view`) and the hidden empty queue column (`queue_column_hidden_empty`). The GUI's `App` keeps the default terminal width, so an empty queue forces Library focus in the GUI too.

## Goals / Non-Goals

**Goals:**

- The GUI Library panel looks and behaves as the canvas specifies.
- The Library loads its content by the same Service steps as the TUI.
- Music is complete and accepted before the other destinations start.

**Non-Goals:**

- No change to the TUI's paint, keys, or behaviour, and no TUI Library code moves.
- No Owner-side, ctrl, or Player change. No new dependency.
- No restyle of the Queue panel. The Queue panel keeps its core-held interaction state.

## Decisions

### D1. The front end owns the Library's interaction; the core owns data and actions

| Front end (Svelte) | Client core (`App` and `CoreThread`) |
| --- | --- |
| Cursor, hover, scroll, open tree nodes | The active destination (`App::tab`) |
| Focus inside the panel (pill row, list, Hero, tracklist) | The selected collection of each destination |
| Filter text, Search query text | The item whose detail the Hero shows |
| The open Hero overlay and item menu | Service data, its loading, and the artwork |
| The Library's keys while it has Panel focus | Panel focus (the `FocusStack`), the actions |

The data selection is core state because the core needs it to decide what to load and what to save at exit. The front end changes it only by a command, and the frame carries it back, so the pill row paints the core's set.

The GUI Library panel uses no TUI component, no `mbv-surfaces` Surface state, no `GuiSurfaceLeaf`, and no `[keys]` action. Its pointer input never reaches the core's gesture recogniser or hit map.

*Alternative:* port the seven TUI destination owners to shared Surface state. Rejected (ADR 0036): it refactors the TUI and binds the canvas behaviour to the TUI's rules. *Alternative:* GUI-only interaction state in the core. Rejected (ADR 0036): every hover and scroll crosses the bridge, and the Library keys still meet the TUI's bindings in the shared router.

### D2. The bridge: one frame section and one command

`GuiFrame` gains `library: Option<GuiLibraryFrame>` (`crates/mbv-gui/src/bridge/frame/library.rs`). It carries the destination tabs, the data selection, and the active destination's content: the pills with their kind (collection or single), the list rows, the Hero's detail, the item menu's entries, the loading and empty states, and the artwork as `data:` URLs from the image cache. A Library list can hold thousands of rows, so the section carries a revision, and a frame re-carries the content only when the revision changes, as `src/artwork.rs` does for the visual slot. A window-content reload's `report_layout` re-arms it. The front end keeps the last carried value.

A new Tauri command, `library(GuiLibraryCommand)`, pushes a `CoreInput::Library` into the core channel, as the other commands do. The variants: open a destination, select a destination's one collection group, show an item's detail, open an album node (load its tracks), take Panel focus, play, play next, add to queue, shuffle an artist, run an item-menu entry, and (Phase 2) run a search query and activate a result. The core thread applies each through one public GUI entry on the `App` (`src/app/gui_library.rs`, beside `gui_client_state.rs`), which calls the existing `App` actions. Item identities are stable Service ids, never row positions.

The projections that build the section are public `App` methods in `src/app/gui_library/`. They read `App` data only, so the TUI's projections and paint do not change.

### D3. Keys: the Library handles its keys first

The front end routes each keydown in this order:

1. While a core overlay is open (the row menu, the track popover, the playback-target chooser, the confirmation modal, the daemon-lost recovery dialog) or prefix mode is armed (both are in the frame), the key goes to the core as today.
2. While a text field in the Library has focus (the `/` filter, the Search field), the field takes the key. Esc closes the field, and Enter accepts it.
3. While the Library panel shows: Tab and Shift+Tab move focus to the next or previous pane (pill row, list, Hero, Queue panel), the canvas's *tab pane*. `1` to `7` open the first to seventh destination tab after Home, the canvas's *1–7 library*. With global search presented, `Ctrl+K` focuses the Search field.
4. While the Library panel has Panel focus, the Library keys below run in the front end.
5. Every other key goes to the core's keyboard router, as today. So Space plays and pauses when no pill has focus, and `[` and `]` seek.

The Library keys (the canvas names the first six; this design adds the movement keys, because the canvas is keyboard-first, note `n1`):

| Key | Effect |
| --- | --- |
| `/` | Open the filter of the list. |
| Enter | Play the item under the cursor, or press the focused control. |
| `n` | Play next the item under the cursor. |
| `a` | Add the item under the cursor to the queue. The add applies the library playback policy's autoload rule to the Library's routes (D8). |
| Space, Alt+Space | On a focused collection pill: select it. One collection stays selected (D6). |
| Up, Down, Page Up, Page Down, Home, End | Move the cursor in the focused list or tracklist. |
| Right, Left | In the tree: open or close the node; on the pill row: move the focused pill. |
| Esc | Close the open filter, overlay, or menu. |

The handler runs before `input.ts`'s forwarder and stops a handled key from reaching it. The front end sends the core no key that it handled. The Queue panel's keys, the GUI-only chords `z`, `q`, and `c`, and every `[keys]` binding keep their effect whenever the Library does not take the key. The GUI-only chords `/` (Queue filter) and `a` (audio popover) work with Queue Panel focus. With Library Panel focus, the Library takes `/` and `a`.

### D4. Panel focus and the arrangement

Panel focus stays in the core's `FocusStack`, and the frame's `GuiFocus` carries it. `CoreThread::new` mounts `ComponentId::Library`. A press inside the Library panel sends the take-focus command, and a press in the Queue panel moves focus as today. Tab across the panel boundary sends the same command. The core sets the stack and `App::panel_focus` together.

The GUI's `App` does not apply the TUI's terminal-width Mini check or its hidden empty queue column: the GUI always paints the Queue panel, and it decides its own arrangement. A GUI setting on the `App` makes `is_mini_view` false and `queue_column_hidden_empty` false for the GUI, so the core's key gates see the stored Panel focus. The TUI's values do not change.

The front end picks the arrangement from the measured Library column width (the window width minus the Queue panel's current painted width, 400 px expanded, 72 px rail, or the width a drag gave it), with the canvas sizes as thresholds: below 480 px (the 320 px list plus the pill row) is Mini, from 880 px (the 320 px list plus a 560 px Hero) is Wide, and between is Narrow. Wide also needs 600 px of height. Mini shows only the panel with Panel focus. Narrow shows the list and opens the Hero as an overlay when an item is picked. Wide shows the Hero beside the list. The thresholds are front-end constants beside the queue panel's state constants. The core does not classify the size, so `mbv_surfaces::breakpoint` stays unused by the GUI.

Both columns are resizable. A drag on the divider between the Queue panel and the Library column sizes the Queue column, and a drag on the divider between the Wide list column and the Hero pane sizes the list column. A double-click returns a divider to its default, and the pointer shows the column-resize cursor over a band that lights while hovered or dragged. The session keeps both widths in front-end module state (`ui/src/lib/bridge/resize.ts`), so they survive tab and breakpoint changes, and the widths persist across launches: each drag writes them to the webview's local storage (`PANEL_WIDTHS_STORAGE_KEY`), and the next start reads them back, with a corrupt value falling back to the defaults. The list column defaults to the canvas's 320 px index 15 % wider, 368 px. The Queue column keeps its 400 px artboard as its minimum, and its maximum leaves the Library column its 480 px Mini threshold, so a drag removes no panel. The list column has no separate pool: it takes the room the Hero pane leaves at its 320 px minimum, so its drag clamp has that one limit. One resolution (`panelWidths`) returns the two painted widths and the Library column they leave, the divider's 6 px included, and the arrangement classifies that same value: the drag and the thresholds cannot disagree, so no arrangement flaps between the paint and the classification. The dividers are mouse-only and send the core no region; the Queue panel's own resize observer re-reports the regions a drag moved.

### D5. Music data: the collection store and the projection

A Grouped Music library's collections are its groups (the group level in `nav_stack`). Its pills are the groups in their level order, and every group pill is a collection pill.

The `App` gains a GUI collection store: per Grouped Music library, the full album list of each selected group, keyed by group id. A group's first selection starts a fetch with the client call that `App::spawn_browse` makes (`get_items_sorted` with the group as parent, sort `SortName`), paged until the total is reached. The completion lands in the store and not in `nav_stack`, so the TUI's navigation state and fetches do not change. The store keeps a loaded group for the session, so switching to a group whose album list has landed needs no fetch. A group whose fetch fails keeps the already-loaded groups in the store and shows the failure line while it is selected.

The Music projection builds the list from the selected group's albums. `mbv_render::group_album_plan` (the function that `App::wide_music_render_ctx` calls, here with no settled catalog) gives each album its `(artist, year, name)` facts and its stable `ArtistKey` from `album_artist_cache`. The projection then builds the union: one artist row per `ArtistKey`, in the artist sort-name order of `mbv_render::sorted_group_album_order` (articles stripped), each with its albums, and each album with its tracks when `album_tracks_cache` holds them. Each artist row carries its sort letter, so the front end paints letter headings and the rail without a second sort rule. An album node that opens sends the open-album command, and the core runs `App::fetch_album_tracks` when the cache does not hold the tracks.

The Hero shows the picked album: the artist header (the artist, the selected collections, the album count, and the track count and total time once the artist's album tracklists have loaded), the album facts, the square artwork, and the tracklist. The core requests the album art with `App::fetch_card_image` and encodes it from the image cache as `src/artwork.rs` does. A picked track picks its album.

### D6. Single-select collection pills

The TUI's Grouped Music pill holds one group selected at all times, so the GUI does the same and drops the canvas SPEC note's multi-select rules. A press on a collection pill selects it and deselects the rest; an Alt-press selects it the same way; Space and Enter select the focused pill. No gesture leaves the row empty, so the show-all selection is gone. The list shows the selected group's albums, and its header reads *Name · sort name*.

The front end sends the pressed group id with the select-collection command. The core stores the choice per destination (`gui_library_groups` holds one group id per library) and loads the group (D5). When the stored group is absent or the library no longer holds it, the first group in pill order is the selection. The launch location saves the choice (D9); the saved file keeps its list shape, and each entry holds the one group.

### D7. The list and the letter rail

The list is the canvas tree: artist rows (30 px), album rows with the year (30 px), and track rows with the track number (28 px), with 24 px letter headings above the first artist of each letter. A press on an artist or album row opens or closes it and picks it; a press on a track moves the cursor onto the row and picks its album — the pick's Hero is album-scoped, so the cursor is the press's visible half, as the Queue panel's click moves the queue cursor. A double-click on a track row of the list plays that track: it sends the play command Enter sends (D8), so the queue is replaced — with autoload on, by the track's album in disc/track order starting at that track; with autoload off, by the track alone. The Hero's tracklist offers no double-click play: a track plays from its hover play button (D8). The cursor and the picked item are different: the cursor moves by keys, and a press picks the item for the Hero. Enter plays the item under the cursor and never picks it: the GUI is mouse-driven for picking, and the TUI's Enter-picks behaviour is its own compromise. The list paints only the rows in view (fixed heights, native scroll), so a long artist list stays fast.

The letter rail shows A to Z beside a list sorted by name. A letter with no rows is disabled. A press scrolls to the first row of that letter and moves the cursor there. The canvas gives the rail no key. Its keyboard path is the `/` filter. The filter narrows the rows to the names that contain the text, without case.

### D8. Hero actions and play next

Play, Add to queue, and Shuffle artist call existing `App` actions: `App::play_or_activate_lib_item`, `App::play_album_track`, and `App::play_music_albums` (with shuffle for Shuffle artist, over the artist's albums in the current union), and `App::enqueue_lib_item`.

The Library's own play and add apply the library playback policy's autoload rule (the Grouped Music tree's track activation): with autoload on, a track whose album the track cache holds replaces the queue with that album's cached playable tracks in disc/track order starting at the selected track, and the add queues the album's cached tracks from the selected track onward; with autoload off, the play and the add act on the track alone. Every other item takes the shared paths unchanged, and the TUI's own add paths keep their per-item appends.

The Library's explicit play and the explicit Shuffle artist skip the TUI's populated-queue replace-confirm: the shared folder and album-expansion paths run with the confirm off, so a play or a shuffle is never gated behind that prompt and a populated queue does not swallow the Hero's buttons. The local saved-playlist protection stays, and its prompt presents in the GUI's confirmation overlay.

The frame carries the playhead's Emby track id from the Queue panel's own authority — the Owner status and the playback queue's item at the active index — so the Hero tracklist row whose track plays shows the canvas's play glyph beside the title, in the accent colour. The library tree shows no playing marker. The row keeps its own fill: a highlight marks focus only, so the playing row takes no green fill.

Play next is new: `App::play_lib_item_next(lib_idx, item)`. It resolves the item with the same route and admission checks as `App::enqueue_lib_item` (folder expansion, playability, route conflict), then sends the Owner's answered Append with `before` set to the slot after the active slot (`QueueOp::Append { items, before }`). With no active slot, or when the active slot is the last one, it sends `before: None`. It never moves a slot that is already in the queue. The TUI has no producer for it.

The Hero's controls show their keys (`n`, `a`). The tracklist's hover controls run play next and add to queue on that track, and the row's hover play button plays it; a double-click on a tracklist row does not play. More actions opens the item menu: the core builds its entries with `App::build_context_menu_for` (the private builder behind `App::open_context_menu_for`, widened to `pub(in crate::app)`), the frame carries them, the front end paints them in the row-menu look of `canvas/Menus.dc.html`, and a chosen entry runs through the id-addressed menu-entry executor (`App::execute_context_action` after the GUI's id-resolved Play and Add-to-queue rewiring, which are never resolved through the TUI cursor). The GUI never arms the TUI's `pending_overlay`. `execute_context_action` finds the library through `App::context_menu_lib_idx`, which needs Library Panel focus and an Emby library in `App::tab`; D4 keeps both true while the Library has Panel focus.

Each carried entry names its index in the shared builder's order, so a front end that paints only some entries (the Hero's More actions) still executes the entry it painted. The Hero's More actions hides the entries its own buttons already send (`Play`, `Play All`, `Add to Queue`) at paint time — the menu names only what no button offers — and paints no More actions control at all when the filter leaves it nothing.

A right-click on a Library list row (artist, album, track) or a Hero tracklist row opens the same item menu as a full list: the `rowMenu` command names the row's stable Service id, the frame's `rowMenu` section carries the TUI menu builder's full entries for that item, and a chosen entry runs through the same menu-entry path. A right-click carries no menu for an item the Service data no longer holds. The music kind's mark entries stay absent, per the context-menu spec's music rule.

### D9. The GUI keeps its own launch location

The GUI's `App` starts with `LaunchRestore::Done`, so the TUI launch state never moves the GUI's tab or Panel focus. The GUI keeps its own file (`mbv_config::load_gui_launch_state` and `save_gui_launch_state`, additive, beside the TUI launch state): the destination, the selected collection of each Grouped Music destination (the Emby group pills and their kept albums), and Panel focus. The Podcasts and Feeds pill rows save nothing here and open on Latest (D12). The core saves it at orderly exit, before `client_exit_teardown`, and never while the window is open. At start, after the catalog lands, the core opens the saved destination, applies its saved sets (a saved group that no longer exists is dropped; when none remains — a saved set the library emptied, and a destination with no saved entry, a fresh launch's case — the first group in pill order is the selection), and sets Panel focus. The restore applies to a destination that holds no selection and never clobbers one the session already made. While the GUI presents only some destinations, a saved destination that it does not present opens nothing: the restore keeps waiting until the user presents one it can open, or ends the session. A start with no saved location — or one that fails to load — restores through the same path: the first presented destination, Library Panel focus, and no saved collection, whose selection is the first group in pill order.

The TUI launch state does not change: the TUI never reads the GUI file, and the GUI never writes the TUI file.

### D10. The Library Status bar

Under the Library column, the Library Status bar shows the canvas's key hints on the left (`/ filter`, `⏎ play`, `n next`, `a queue`, `tab pane`, `1–7 library`) and the location on the right: the destination, the selected collection's name, and the picked item's artist or title, joined by ` › `. The hints are the GUI's fixed keys (D3), so they are fixed text. While prefix mode is armed or a toast shows (the shared `GuiStatusBar`), that replaces the hints, and the location stays. While the Library panel does not show, the Queue footer paints the prefix and the toast as today.

### D11. The service bootstrap becomes a shared Client step

The TUI-only bootstrap steps move into one `App` step, `App::start_client_services`, that both Clients run once after the attach: the Emby startup worker, the Audiobookshelf startup worker, `start_feed_fetch`, and capability registration. `Model::spawn_startup_services` calls it in place of its body, at the same point, so the TUI's order and timing do not change. The GUI core thread calls it in place of `start_emby_client_fill`, which is deleted with its worker and tests.

The GUI keeps its playback-target discovery. The client fill starts `spawn_sessions_load` and `spawn_cast_discovery` for a cached client and on its completion; the full Emby startup starts neither. So the GUI core thread starts both after `start_client_services` when the attach brought a cached Emby client, and in its `drain_startup_workers` host when the drain reports a successful Emby startup (`StartupWorkerDrain` gains `emby_started`; the TUI host ignores it).

On a launch with a cached Emby client no Emby startup worker runs, and only `App::fetch_home` builds the library tabs. So the `App` half of `Model::fetch_home_at_startup` moves into `App::load_home_at_startup() -> Option<HomeContent>`: `fetch_home`, then on success `spawn_home_recently_added(Emby)` and the status clear, and on failure the "Couldn't load home" toast. Both Clients call it right after `start_client_services`; the `Model` keeps the Home half (`home_content.loading` and the assignment). The GUI drops the returned content until Home lands (unit 10). `init_idle_feed` joins the shared step in unit 10.

### D12. Phase 2: the other destinations and Search

Each destination paints the Music slots with its own data: a pill row, a list, a Hero (with landscape, portrait, or square art, or no Hero), and an optional Workspace list in the Hero (Shows' seasons and episodes, Audiobooks' chapters). Each unit adds its projection in `src/app/gui_library/` from the `App` data that the Context section names, and its commands. Home's content moves from `Model::home_content` into the `App` (the TUI reads it there; its paint does not change), and the GUI stores the content of `App::load_home_at_startup` and of the startup drain's `home`. Each unit's first step reads its destination's data path and records it in this design before the code.

Home's data path (unit 6.1): `App::home_content` (`src/app/state/app_struct.rs`, type `state::playback::HomeContent`) holds the Home content — the Continue Watching items and the `loading` flag. `App::fetch_home` (`src/app/dispatch/library/load.rs`) computes the snapshot, and `App::load_home_at_startup` (`src/app/dispatch/session/client_startup.rs`) stores it on the App at launch. `App::drain_startup_workers` (`src/app/client_drains.rs`) replaces the stored snapshot with a rebuilt Emby bootstrap's snapshot and hands the same snapshot back to the Client. App-internal refresh writers send the snapshot through `ModelContentEvent::HomeContentRefreshed`, and the shell's assignment lands in the same field with its eviction and owner push.

Home's `Recently added` data path (unit 6.2): `App::home_recently_added` (`src/app/state/app_struct.rs`, `state::app_struct::home_recently_added`) holds the per-source rows, and its store, accept, evict, and merge logic lives there too (`App::accept_home_recently_added`, `App::home_recent_rows`, `App::home_stable_target`). The fetched event's App drain arm stores the rows, so a Client that keeps no shell reads the same store as the TUI shell. A rebuilt startup-drain snapshot evicts the sources its library set dropped on the App before the Clients project it.

The GUI Home design (user-approved live-test round): Home paints one flat list in the Music list slot. The two sections are heading rows in that list — Continue watching first, then Recently added — and each row carries its date in the gutter, with no pills. The selected row's Hero shows beside the list; Home has no Workspace. Continue watching rows paint their art in Phase 2; the Audiobookshelf and Feed rows paint without art.

Shows' data path (unit 7.1): the view mode, series, and season selection lives in `App::gui_tv_shows` (`src/app/state/app_struct.rs`, type `gui_library::GuiTvShowsSelection`), and `App::gui_tv_open` seeds its mode with the default `resolve_tv_content_mode` computes. `gui_tv_open` and `gui_tv_set_mode` load the root level through the TUI's own `apply_tv_letter_mode` — the Latest and Upcoming spawns and the All series refresh — and `gui_tv_select_series` and `gui_tv_select_season` run `fetch_series_detail` and `fetch_series_season_episodes`, the loaders whose triggers lived only in the presenting Client's workspace push. The fetched events land App-side: the `EmbyLatestSnapshotFetched` arm fills the Latest root level through `App::apply_tv_latest_snapshot` (the write the shell's `update_emby_latest_snapshot` joins), and the `TvUpcomingSnapshotFetched` and `TvUpcomingSnapshotFailed` arms run the App's own accept and failed-mark writes. The shell drain keeps only its snapshot store and its projection push, so the TUI applies each write once and the GUI applies it through `App::drain_lib_event`. The later core surface's commands apply these actions, and its projection reads these fields. A press selects the row, so the Hero shows it. Enter or a double-click plays the row through `App::home_play_target` (unit 6.3), and `n` and `a` enqueue it through `App::home_enqueue_target`.

The GUI Shows design is D14: it replaces the flat-series design this paragraph first named, and it follows the Music base and the TUI. Latest paints the flat newest-episodes list, and Upcoming paints the flat premieres list with no Hero.

The GUI Emby library design (user-approved): an Emby library that is neither grouped Music nor Shows — movies, boxsets, music videos, home videos, and the other types — paints the Music slots with its own data: a list and a Hero with no Workspace. A plain library's list is flat and sorted by name, shows the letter rail, and holds no pills: the rail replaces the TUI's letter-range pill row, as it does for Shows, and the Hero's art shape comes from the artwork policy (`emby_artwork_policy`, `crates/mbv-components/src/library_panel/hero.rs`). A library in feed-group mode (`feed_view_libraries`, `src/app/dispatch/feeds/feed.rs`) paints a pill row of All and each root folder that holds items — the TUI's `FeedHomeVideoSelection::All` and `Folder` (`crates/mbv-ui-model/src/feed.rs`) — and the pills are single-select (D6). Its list is in the server's date order with no letter rail — All newest first and a folder oldest first, as the TUI fetches them — and a press on a pill loads that group's items. The union of selected groups is dropped, as for Music: the TUI's feed-group view holds one selection. Enter plays the row under the cursor; a folder or a boxset plays through the TUI's folder-play rule (`App::play_or_activate_lib_item`, `src/app/dispatch/navigation.rs:20`), so the Hero replaces the queue with the folder's items and the Library opens no nested list. `n` and `a` work as in Music (D8).

The GUI Podcasts and Feeds design (user-approved): each destination paints the Music slots with a pill row, a date-gutter list, and a Hero with no Workspace. The pill row is single-select (D6): Latest plus one pill per show (Podcasts) or per subscription (Feeds), with Latest the default, as the TUI's one-valued `PillSelection` is (`crates/mbv-ui-model/src/audiobookshelf_browse/podcast.rs:40`). Latest merges the episodes of every show — or the entries of every subscription — newest first with undated rows last, and a show or subscription pill scopes the list to that one collection. The list shows no letter rail, because it is sorted by date. The Podcasts Hero is the episode with square cover art, its facts, and its description (`hero_content_abs_episode`), and the Feeds Hero is the entry's title and duration with placeholder art (`hero_content_feed`, `crates/mbv-components/src/library_panel/hero.rs:631`). Enter or a double-click plays the row as the TUI does: the queue is replaced through the shared admission rule of that Service, and `a` adds the row to the queue. The TUI's state pills (All, Unplayed, and Played, and the Feeds watched filter) and the saved pill selection in the GUI launch file are dropped in Phase 2.

Search: the top bar's Search field (*Search everything*) sends its query with the search command. The core runs `App::spawn_search_sidebar_query`, and the GUI tick host runs `drain_search_results` in place of its no-op. The results paint below the field in the list-row look. A plain Emby library's data path (unit 8.1): the open runs the TUI's own activation — `App::set_library_tab` settles the tab and calls `App::activate_library_position`, which restores a saved position or seeds the root level and starts `App::spawn_browse` (`crates/mbv-ui-model/src/browse.rs` levels, `src/app/dispatch/library/browse/loading.rs`); the completion rides `LibEvent::Browse(BrowseEvent::Loaded)`, and `App::handle_lib_loaded` fills the `nav_stack` level, captures `library_total`, and for a library over `LIBRARY_PILL_THRESHOLD` applies the default letter-range filter with a scoped refresh, while a smaller library's further pages arrive as `PageAppended` as the cursor moves. Because that path cannot serve the full flat list the letter rail reads — the bucketing above the threshold and the cursor-paced paging below it both leave rows unloaded — the GUI loads the whole root list through the Music store's precedent (D5): `get_items_sorted` with the library's default item types and the `SortName` ascending sort, paged to completion into the App's `gui_emby_roots` store, which lands outside `nav_stack` on the new `LibEvent::GuiEmbyRootItems` arm. An Audiobookshelf book library's data path (unit 9.1): the catalog lands App-side without a new channel — the shared startup's completion runs `start_audiobookshelf_catalog_fetches`, the `BooksFetched` arm pages the chain inside `App::handle_audiobookshelf_books_fetched`, the `BookDetailLoaded` arm fills the browse state's `detail_cache`, and the book progress lands through the Player event drain's `reconcile_audiobookshelf_book_progress`; the GUI tick's `drain_lib_event` runs the first two, so no arm drops a payload and the TUI never double-applies. The GUI owns one selection store per book library, `App::gui_abs_libs` (`gui_library::GuiAudiobooksSelection`, the picked book's `library_item_id`), beside the browse state's TUI `selected_id`, which it never writes; `gui_abs_open` starts the TUI's own book catalog load through the F5 refresh path when the catalog is unloaded, `gui_abs_select` stores the pick and runs the TUI's detail loader, and `ensure_gui_abs_selection` is the frame path's trigger for the default first book's detail. `GuiDestinationKind::Audiobooks { lib_idx }` presents the book libraries in the tabs, the open-position gate, and the launch restore; a podcast library presents nothing until row 10.1, and a saved Audiobookshelf location's resolution waits while the Audiobookshelf catalog is still landing. The GUI Audiobooks design (orchestrator decisions, extending the user-approved Shows and Emby designs): the list is the flat book list in the TUI's sort — author sort key, then title — with the A-Z letter rail over the author sort key (`#` for a digit or symbol), and no pills, because the rail replaces the TUI's eight surname buckets as it does for Shows and the plain Emby libraries. The book Hero is portrait cover art with the TUI Hero's facts (title, author, duration, `Finished` or `N%`) and no narrator, series, or description, and its Workspace is the book's chapter rows — title and duration, with `AudioFile` `Part N` rows when the book holds no chapters — and the current chapter marked while that book plays. Enter or a double-click on a book plays it from its saved position; Enter or a double-click on a chapter row plays or seeks from that chapter, the TUI's ActivateChapter rule; `a` enqueues the book, `n` is consumed and does nothing for books, and this unit adds no mark-played entry. Every play and enqueue honours `player.can_admit_audiobookshelf()`, and a refusal flashes the TUI's owner-unavailable toast.

A Podcasts library's data path (unit 10.1): the show catalog and the per-show episodes land App-side — the shared startup's `start_audiobookshelf_catalog_fetches` starts the show-list chain, the `ShowsFetched` arm pages it into `AudiobookshelfBrowseState` and re-arms the bounded fan-out (`start_audiobookshelf_podcast_fan_out`, `MAX_PODCAST_DETAILS_IN_FLIGHT`), and each `DetailFetched` arm caches that show's episodes in `detail_cache`; the GUI tick's `drain_lib_event` runs the same arms, so no payload is dropped and the TUI never double-applies. One shell-only half produced App state: the Latest shelf's lazy one-shot spawn, which now lives in `App::ensure_audiobookshelf_latest_shelf` and is called by the shell's projection pass and by the GUI's frame path, so both Clients' App data hold the same shelf; the latest-marker acknowledgement and the hero-image projection stay the shell's, because they write Model state and paint. The GUI owns one selection store per podcast library, `App::gui_podcast_libs` (`gui_library::GuiPodcastsSelection`: the pill `Latest` or `Show(show_id)`, default Latest, and the picked episode by the provider's `(library_item_id, episode_id)` identity), and its one shared write is the browse state's `committed_show_pill` scope that the fan-out reads; the browse state's own selected show and episode stay the TUI's. `gui_podcast_open` starts the TUI's show-list chain when the catalog is unloaded, `gui_podcast_set_pill` stores the pill and starts the loads that pill needs, `gui_podcast_select` stores the episode the Hero shows, and `ensure_gui_podcast_selection` is the frame path's trigger for the selected pill's loads. A Feeds data path (unit 11.1): the configured subscriptions land on the App at construction, because `App::sync_feed_subscriptions` copies `config.feeds` into `App::feed_tab`, and the shared `App::start_client_services` step starts the one fetch. ### D13. Each pill keeps its last album, and the Hero defaults to the first

The Hero shows the album the selected group's pill last showed. The core keeps one pick per library and group (`App::gui_library_picks`): the window content's `showDetail` sets the selected group's pick. A group with no pick, or whose kept album its list no longer holds, shows the first album in list order. The default makes the Hero paint as soon as a collection's albums land, so the window never opens blank.

The picks persist in the launch file beside each destination's selection (`GuiDestinationCollections.picks`, keyed by the stable group id and album id). The field is `#[serde(default)]`, so a file written before it loads with no picks, and the file version does not change. The restore applies the picks with the group list, and it never overwrites a pick the session already made.

### D14. Shows follows the Music base and the TUI (supersedes D12's first Shows paragraph)

A live-test round showed that the first Shows design deviated from the TUI in every slot: no tree, a Hero Workspace that never loaded an episode, the generic Emby metadata producer instead of the series producer, a 300 px landscape art box, and no list header. Music is the base for the other destinations, and the TUI's TV tab is the behaviour model. The Shows destination therefore takes the Music slots:

- **The list column is the Music tree** (D7): series nodes (30 px), season nodes (30 px), and episode leaves (28 px), the 24 px letter heading over the first series of each letter, the A–Z letter rail, and the `Series` title with the active mode's name as the selection label and the `/` filter field, in the Music header's shape. An expandable node paints the Music chevron. The cursor steps over nodes and leaves and never rests on a heading. A press on a node opens or closes it and selects it for the Hero; a press on a leaf only moves the cursor there, and a double-click on a leaf plays it, because the series Hero carries no episode selection. Opening a series sends the series-detail load; opening a season sends that season's episode load. Right and Left open or close the node under the cursor, the tree meaning design D3 gives them, and they still walk the pill row while a pill has focus.
- **The Hero uses the TUI's series producer**: `hero_content_series_with_episode(series, None, false, seasons)` — the genre, the show's year range (else the release date), `N Seasons`, and the network — and no duration row while the Workspace has no focus. The Latest mode keeps `hero_content_emby`, as the TUI's Latest hero does. The Workspace-focus overlay that swaps the rows, overview, and artwork for the selected episode's is not carried: the GUI Hero band paints show-level facts beside a Workspace with its own cursor, and the overlay would need the core to carry a second fact block. It is recorded as a follow-up, not painted now.
- **The Hero is the Music Hero's frame** (`LibraryHeroFrame`, the one frame Music and Shows paint (Podcasts, Audiobooks, and Feeds too, headerless), as the TUI paints both through one `HeroContentData` and one Workspace): the header band is the series (kicker, title, and the producer's rows — genre, years, season count, network — joined as its facts line), the detail block is the series' `Primary` poster beside the selected season (the album's twin: its name and episode count) and the series' overview, and the list band is the Workspace. The artwork is the item's `Primary` image, not the landscape chain: a series declares the portrait arm, and the fetched image's own pixels re-arm the shape as in Music. The landscape arm (a full-width 16:9 still above the text) remains for an image whose pixels are wide, such as an episode's `Primary` still in the Latest mode.
- **The Workspace loads eagerly**: the season pills and the selected season's episodes are the Hero's Workspace (D12's rule, kept), and the frame path's `ensure_gui_shows_workspace` loads the selected series' detail and its selected season's episodes, so the Hero paints a Workspace on arrival. D12's original chain loaded the detail only, so the first season was selected but never fetched and the Workspace painted empty. The season pills start on the first season and are not kept across a series change.
- **The pills carry the TUI's labels**: `New`, `Upcoming`, and `All`, single-select, one always selected. The A–Z rail stands in for the TUI's A-I/J-R/S-Z letter-range pills, as D7 and D12 already decide, so a large library shows no range pills. The Upcoming mode's failure line carries the TUI's text and names the pill as the retry.
- **The Hero and the rows carry the Music action set**: a right-click on a series, a season, or an episode row opens the item menu at that item's stable Service id, and the Workspace rows keep their hover Play next and Add to queue controls. A series has no whole-series Play: the TUI has no play path for a series, and the GUI does not invent one.
- **The frame carries the tree**, not flat rows, as the Music section carries artists → albums → tracks: a series node holds its seasons, and a season holds its episodes or `None` while its load has not landed. Row identities stay stable Service ids.

### D15. One base slot per Library control, and the rail stands in for letter buckets

The live-test round that produced D14 showed a second failure beside the Shows slots: each destination had re-implemented the slots Music already owns. Five pill rows painted the same button, six lists painted their own header or none, and every Hero held its own artwork-box arithmetic, so a fix landed in one tab and missed four. The rule is now one base component per Library control, in `crates/mbv-gui/ui/src/lib/components/`:

- **`LibraryPillRow`** owns the canvas's single-select pill form. Music's collections, Shows's modes, an Emby library's folders, Podcasts's views, and Feeds's views pass their carried pills, the key a press names, and the destination's own attribute suffix; none paints a button of its own.
- **`LibraryListHeader`** owns the `Artists`-shaped header: the list's title, the carried selection's label beside it, and the `/` filter field under both, with the destination's own title and label attributes preserved.
- **`LibraryListNotice`** owns the one-line loading, failure, and empty notice above a list's rows.
- **The Hero's artwork arm** keeps its one rule: landscape fills the Hero content width at 16:9 above the title and meta block, and portrait and square keep the canvas's 300 px box beside the text. A destination that paints a Hero adopts that rule rather than restating it.

A destination adds data and a command, never a control's look. A destination that needs a control the base lacks adds it to the base, so the next destination inherits it.

**The TUI's `New` pill stays off the Emby tabs.** The TUI paints `New` first in an Emby library's selector row, but that scope reads `latest_items` from the shell's per-library latest snapshot, and only a TV library's Latest root fills that snapshot (`src/app/shell/emby_library_content.rs:191`, `src/app/dispatch/library/browse/tv.rs`). A plain Movies library therefore paints `New` over an empty list today. The GUI paints no control whose list it cannot fill, so an Emby library's pill row keeps its real modes — a feed-group library's `All` and its folders — and records `New` as a TUI gap rather than a GUI loss.

**Letter buckets stay as the rail.** The TUI's letter-range pills (Movies `A–C` … `V–Z`, `#`; TV `A–I / J–R / S–Z`) and the Audiobookshelf surname buckets are replaced by the A–Z rail on every destination (D7, D12, D14). The user accepted the rail as the letter control after the Shows re-alignment, so no destination paints letter pills; the rail's finer letter grain does the same job without a second control beside it. A pill row therefore carries only the real modes: Shows `New`/`Upcoming`/`All`, an Emby feed-group `New`/`All`/folders, an Emby plain library `New`/`All`, and Podcasts `Latest` plus the three state pills plus each show.

### D16. Every interactive control answers the pointer

The GUI painted no hover at all: a pill, a tab, a row, a rail letter, and a Hero button looked the same whether the pointer was on them or not, while the canvas's own states (`--canvas-selected`, `--canvas-action`) covered only the picked row and the hover actions. The rule is now one stylesheet rule in `app.css` rather than a per-component style, so a control cannot be added without the hover:

- **One veil, not one fill.** `--canvas-hover-veil` is the palette's foreground `#d3c6aa` at 14 % over whatever fill the control paints. The components set their fills inline (`style:background`), so a stylesheet fill would lose; an *inset box shadow* composites above that fill and below the label. A bare ghost button, a picked row, an accent Play button, and the filter field's frame each keep their own colour and still light up.
- **The selectors are the interaction roles**, not a class: `button`, `[role='menuitem']`, `[role='tab']`, `[role='option']`, and the filter field's `label:has(> input:hover)`. Disabled controls keep the arrow and no veil.
- **The seekbar is the one exception.** It answers the pointer with the trickplay tile preview, and a veil over its 60 px box would tint the elapsed and remaining labels with it.

## Risks / Trade-offs

- [A window-content reload resets the Library's cursor, scroll, and open nodes] → The data selection survives in the core, so the destination, the pills, and the Hero's item stay.
- [The Library keys are GUI keys that `[keys]` does not configure] → Accepted (ADR 0036). Every key the Library does not take still reaches the router and `[keys]`.
- [A union of selections makes one fetch per selected group] → The Music and Emby stores keep each loaded group's data per group for the session (D5, D12), and Podcasts and Feeds hold no union: their pills are single-select (D6).
- [The shared bootstrap touches TUI startup code] → The TUI keeps its call order; its startup and lifecycle tests are the proof.
- [The thresholds may feel wrong live] → They are front-end constants; the Music gate's live test checks them.

# Design: add-gui-library-panel

## Context

See `proposal.md` for the why and `specs/gui-client/spec.md` for the requirements. The canvas reference is a verbatim local copy of all the canvas files in `openspec/changes/add-gui-library-panel/canvas/`: `canvas.json` (the canvas index, with the SPEC note on multi-select pills), `Library.dc.html` (*Library — Music › Hip-Hop*), `Main.dc.html` (*Queue panel — expanded*), `Collapsed.dc.html` (*Collapsed states*), and `Menus.dc.html` (*Track popover, row menu, drag*). The copy is a source to read, not a page to open: its `./support.js` runtime belongs to the canvas host. To see it rendered, open the live canvas, `https://claude.ai/artifact/D8uLGS6NyCeHd6ed7PHgsr` (the *Library — Music › Hip-Hop* artboard).

What the code holds today:

- Every TUI destination owner gives the Library panel one typed paint input, `LibraryPanelContent` (`crates/mbv-components/src/library_panel/content.rs`). It has a `SelectorRow`, a `ListSlot` (`Media`, `Empty`, `Search`), and a `HeroSlot` (`Absent` or `Pane`). A `HeroContent` has `HeroFacts` with an artwork shape arm, and an optional `Workspace` (header, selector, list).
- The interaction state of the Library is in the TUI components: `LibraryPanel`, the seven owners (`music_content`, `tv_content`, `emby_library_content`, `home_content`, `book_content`, `podcast_content`, `feeds_content`), `tab_panel`, `inline_search`, and `search_sidebar`. `mbv-surfaces` holds only queue, queue playback, status bar, list, media list, seekbar, gesture, hit map, focus stack, capacity, and breakpoint.
- `mbv_surfaces::breakpoint` defines `Mini | Narrow | Wide`, `classify`, and `hero_side_by_side`. No Client calls them yet.
- The GUI core thread owns an `App`, emits `GuiFrame`, and applies `LayoutReport` (`docs/architecture/gui-client.md`). The guide's surface order (*Adding a surface to the GUI*) applies to every surface in this change.
- The launch state is `TuiLaunchState` (`crates/mbv-config/src/launch_state.rs`). The `App` loads it at construction for both Clients, but only the TUI saves it: `Model::teardown` builds the snapshot from the mounted TuiRealm `LibraryPanel` (`Model::launch_state_snapshot`), and the GUI's `App::client_exit_teardown` saves nothing by design. The selector is one `SelectorIdentity` for the active destination.
- **The GUI loads no library content.** `CoreThread::new` (`crates/mbv-gui/src/core_thread.rs:245`) runs only `App::start_emby_client_fill`, an authentication-only worker (`src/app/dispatch/session/command.rs:9-16`). The TUI's bootstrap (`Model::spawn_startup_services` in `src/app/shell/run/drains.rs:521`: the Emby and Audiobookshelf startup workers, `start_feed_fetch`, capability registration; then `fetch_home_at_startup` and `init_idle_feed`, `src/app/shell/run.rs:271-276`) is TUI shell code. `docs/architecture/gui-client.md` (*The attach states*) requires that a library port first factor it into a shared Client step and not copy it into `mbv-gui`. So `App::libs` stays empty in the GUI today.
- **Library requests run only in the TUI shell.** Every Library `ShellRequest` (Music in `src/app/shell/messages/music.rs`, Emby browser, TV, Home, Audiobookshelf in `src/app/shell/messages.rs:53`) is handled by `Model`, and each handler mixes an `App` effect with a TuiRealm step (`push_music_workspace_content`, `music_owner()`, `open_library_hero_overlay`, the pending re-anchors and track-focus requests held on `Model`). The GUI's dispatch (`App::handle_gui_queue_shell_request`, `src/app/input/gui.rs:305`) drops every one of them in its logged catch-all arm.
- **The `App` stores Panel focus.** `App::panel_focus` and the ephemeral `mini_view_focus` are the stored record; App effects write it (for example `MusicTrackActivate` sets Library focus), and the key policy reads it. The TUI feeds the core `FocusStack` from `App::effective_panel_focus()` on each sync (`Model::apply_focus_stack`, `src/app/shell/focus.rs:78`). The GUI core thread sets its stack directly (`core_thread.rs:239`, `:466`).
- **The `App` holds the selected Music group.** A Grouped Music library's group is the resting cursor of the group level in `nav_stack`; `App::switch_music_group` (`src/app/dispatch/music.rs:106`) pops the one album level and fetches the new group's level in its place. No per-group level cache exists. An Emby library in feed-group mode also keeps one selected group in `App` state (`feed_home_video_selected_group_index`). Podcasts keep each show's episodes for the session (`podcast_content.rs:375`).
- **Launch restore is half shared.** The `App` settles the tab (`LaunchRestore::TabSettled`, `src/app/dispatch/library/cw_library_tab.rs:147`); the pill and Panel-focus half is `Model::reanchor_pending_launch_destination` (`src/app/shell/library_panel.rs:228`), which reads the mounted TuiRealm `LibraryPanel`.
- **The GUI tick host leaves the Search phases empty.** `tick_inline_search_clock`, `tick_search_clock`, `handle_service_request`, and `drain_search_results` are documented no-ops in `crates/mbv-gui/src/core_thread/tick_host.rs`.

## Goals / Non-Goals

**Goals:**

- One Library painter for each slot in the GUI, used by every destination.
- The TUI's interaction rules run once, in the Client core, for both Clients.
- Music is complete and accepted before the other destinations start.

**Non-Goals:**

- No change to the TUI's paint, key output, or behaviour.
- No Owner-side, ctrl, or Player change. No new dependency.
- No canvas artboards for the other destinations: their look derives from the Music slots (proposal).
- No restyle of the Queue panel.

## Decisions

### D1. Port each owner's state into one Library Surface state in `mbv-surfaces`

A new `mbv_surfaces::library` module holds `LibrarySurface`: one `DestinationSurface` per mounted destination. The tab selection is not in it: `App::tab` and `App::tab_scroll` own it (`src/app/state/app_struct.rs:280`), and `TabPanel` is already an adapter that projects them one-way and keeps only hover and its hit regions (`crates/mbv-components/src/tab_panel.rs:1-9,55-64`). Both Clients read `App::tab` for the active destination: the GUI frame, the projections, and the shared snapshot builder. Panel focus between Library and Queue keeps its existing parts: the `App` stores it (`App::panel_focus`, with `mini_view_focus` in Mini), and the core `FocusStack` derives the focused surface from `App::effective_panel_focus()` (`client-interaction-core` "The core focus stack is the one focus authority"). The GUI core thread follows the TUI's `Model::apply_focus_stack`: each step feeds its stack from `App::effective_panel_focus()`, and a press or key that moves Panel focus calls `App::set_panel_focus`, never the stack directly. `LibrarySurface` holds no copy, and `LibraryPanel`'s `panel_focused` stays a paint input read from the focus stack.

**The GUI does not hide an empty Queue column.** `App::effective_panel_focus()` and `effective_panel_mode()` have a third input: `queue_column_hidden_empty()` (`src/app/state/panel_focus.rs:44-79`) forces Library focus and `LibraryOnly` when the displayed queue is empty, because the TUI hides that column. The GUI always paints the Queue panel (main spec `gui-client`, the empty-queue state), so in the GUI that rule would pin focus to Library and make `PanelFocusLibraryBoth` and `PanelFocusQueue` (`key_policy.rs:320-325`) dead. So the `App` gains `layout_source: LayoutSource`, `Terminal` (the TUI, the default) or `Gui { class: Option<BreakpointClass> }`, which `CoreThread::new` sets before its first step and the D4 report updates. With `Gui`, `is_mini_view()` reads the class (`Mini`; `None` before the first report is not Mini) in place of `terminal_width`, and `queue_column_hidden_empty()` returns false, so both the focus and the mode keep the stored values. With `Terminal`, nothing changes. The focus between the browser pane and the Workspace inside a destination is that destination's Workspace focus bit in `DestinationSurface`. A `DestinationSurface` holds a `SelectorSurface` (pills, selected set, focused pill), the browser list state (the existing `list`/`media_list` Surface types, and the tree's logical state for Music and Shows: cursor, viewport offset, open nodes, filter; `TreeBrowser` does not move whole, because it imports ratatui and holds paint retention, configured rects, and marquee state, `crates/mbv-components/src/list/tree_browser.rs:16,142-168`, which stay in the component as adapter geometry, `crates/mbv-surfaces/src/lib.rs:5-7`), the Workspace list and selector state, the Workspace focus bit, and the filter draft. `SearchSurface` holds the Search sidebar's query, type filter, and result list.

The TUI components become adapters over this state (the ledger rule in `docs/architecture/interactive-surface-ledger.md`). They keep geometry, paint policy, and raw-input translation. Each port is behaviour-preserving: the existing TUI paint, tick, and key tests are the proof and stay green unchanged. Tests that observe a derivation that a port moves out of the component (design D2) move with it, as stated there.

**The key rules move with the state.** Library navigation keys are component-local today: each owner's `on_key` matches `[`/`]`, `/`, Enter, the list movement keys, and (in Music) the Ctrl+P, Ctrl+A, Ctrl+S, Ctrl+W, and Ctrl+R item chords as fixed `Key` values (`music_content/owner.rs:400-530`) (for example `music_content/owner.rs:413`, `podcast_content/panel.rs:253`); the registry declares none of them. Each port moves the owner's key interpretation into a `key(&mut self, KeyEvent) -> LeafKeyResult` on its `DestinationSurface`, the precedent being `QueueSurface::key` (`crates/mbv-surfaces/src/queue.rs:415`). The TUI owner's `on_key` and the GUI Library leaf both delegate to it, so the GUI gets every TUI Library key with no second copy, once the GUI router lets the key reach the leaf (design D15). The existing TUI key tests are the proof. "Raw-input translation" in the adapter means only crossterm-to-`KeyEvent` and mouse-to-gesture translation.

*Alternative:* the GUI core thread drives the TUI components directly. Rejected: the components are TuiRealm types and own their state, which the guide forbids a second Client to reimplement or reach into.

### D2. One GUI-neutral slot-content projection, used by both Clients

`LibraryPanelContent` cannot feed the GUI: it is an `mbv-components` type that borrows `&mut dyn PanelList` from the TUI's mounted owners, and `mbv-gui` cannot depend on `mbv-components` (TuiRealm and ratatui) and has no owner map. Every GUI frame section is built in `crates/mbv-gui/src/bridge/frame.rs` from public `mbv::App` projections plus GUI state.

So the slot content gets a plain model, `LibrarySlotContent` in `crates/mbv-ui-model/src/library_slots.rs`: the selector row (pills with stable identities, kinds, selected set, focused pill), the list rows (tree nodes or media rows, with non-selectable letter headings), the Hero (facts, artwork shape, artwork image key, actions with their action ids, overview, credits), and the Workspace (header, selector, rows). It holds owned data, no borrow and no `PanelList`. For each destination, a public `App` projection in `src/app/state/projection/` builds it from the `App`'s Service data (`App::libs` and its `nav_stack`, as `music_wide.rs` already does for Music, which the shared bootstrap fills in both Clients, design D13) plus that destination's `DestinationSurface`.

The derivations that build slot content today in the owners (`MusicWorkspaceComponent::panel_content` and `resolved_hero_data`, `TvContent`'s selector and Hero, and the five siblings) move into these projections. Each TUI owner then builds its `LibraryPanelContent` from the same `LibrarySlotContent`, so each derivation exists once and the TUI paints exactly what it paints today. The proof is in two parts. The component tests that set owner context and assert a derived result (for Music, `music_content/tests.rs:328-349` for the pills and the Hero assertion of `tests.rs:352`, from `context.artist_detail`) test a derivation that leaves the component; each moves to the projection's tests with the same fixture and the same expected result, and is deleted from the component. A test that also asserts behaviour that stays in the component is split, not moved: the `tests.rs:352` test keeps its `track_list.rows().is_empty()` and `workspace_track_item("beta-track").is_none()` assertions (`:395`, `:402`) in the component, because `workspace_track_item` is a live lookup with production callers (`music_content/owner.rs:599,608`, `workspace.rs:433`, `interaction.rs:92`). The TUI paint, tick, and key tests do not observe the derivation directly and pass unedited.

The core thread builds `GuiLibraryFrame` (`crates/mbv-gui/src/bridge/frame/library.rs`) from `LibrarySlotContent` plus the adopted Surface state, once per emitted frame. It carries: the breakpoint class, the tabs, the selector row (pills, selected set, kinds), the list rows of the viewport only, the letter-rail letters present, the Hero (facts, artwork shape, artwork image reference from the image cache, actions with their key hints, overview, credits), the Workspace (header, selector, viewport rows), whether the Hero overlay is open, the inline filter (open or closed, and the query text), and the Search section. Text stays glyph-free. The destination never reaches the frame as a key the front end branches on: the front end paints only the slots the frame carries (slot content with no Hero gives no Hero).

### D3. Regions, list ids, and the leaf

`LibraryTargetId` mirrors `LibraryHitTarget` variant for variant; `LibraryHitTarget` is new in `mbv_surfaces::library`, beside `QueueHitTarget` and `StatusBarHitTarget`: tab, pill, pill clear, list row, letter, Hero action (play, play next, add to queue, shuffle artist, more actions), Workspace pill, Workspace row, Workspace row action, overlay close, Search field, Search result. `ListId` gains `LibraryList`, `LibraryWorkspace`, and `SearchResults`; each reports whole rows as capacity. A `GuiSurfaceLeaf` for the Library resolves gestures against the reported regions and emits the same semantic `Msg`s as the TUI Library pointer path. A target the GUI has not ported is a documented no-op. The canvas's Collection options control has no effect in the canvas or in the TUI, so the GUI does not paint it (no-stub rule) and it has no target.

### D4. The breakpoint is classified on the Library column width

The front end measures the Library column (the window width minus the Queue panel's current width, 400 px expanded or 72 px rail) and reports its width and height in `LayoutReport` beside `container_size`. The core classifies it with the shared `mbv_surfaces::breakpoint::classify` and `hero_side_by_side`, their first non-test caller, and the frame carries the class as a GUI bridge enum (`crates/mbv-gui/src/bridge/frame/library.rs`), so `mbv-surfaces` needs no serde. The front end arranges the panels from the frame's class. Thresholds, from the canvas sizes: `mini_below = 480` (the 320 px list plus the pill row's minimum) and `wide_from = 880` (the 320 px list plus a 560 px Hero: 300 px art, 64 px padding, and the text column). The height guard for `hero_side_by_side` is 600 px. In Mini, the panel with Panel focus takes the whole window. Mini focus is ephemeral, as in the TUI: the reported class feeds the `App`'s Mini check in place of the terminal-width test (`src/app/state/panel_focus.rs`), so a focus move in Mini writes `mini_view_focus`, not the stored Panel focus, and does not survive a widening. The core uses the class for the frame, for Mini focus, and for the Hero overlay rule: as in the TUI (`!is_right_panel_wide()` in `src/app/shell/messages/music.rs`), the Hero opens as an overlay in every arrangement that does not show it side by side, Mini included. The trade-off: after a resize, the arrangement follows on the next frame, not in the same paint; the queue panel's own four states keep their front-end measurement.

*Alternative:* classify on the window width. Rejected: the `z` rail frees 328 px, and the Library should use it. *Alternative:* classify in the front end. Rejected: the core needs the class for Mini focus and the Hero overlay, and the shared classifier would stay dead.

### D5. Multi-select is a selector kind rule in the core

`SelectorSurface` marks each pill as a collection pill or a single pill. The owner sets the kind when it builds the pill row:

| Destination | Collection pills | Single pills |
| --- | --- | --- |
| Music (grouped) | every group pill | none |
| Podcasts | every show pill | New, the played-state filters |
| Feeds | every subscription pill (`FeedGroupKey::Feed`) | Latest, the filters, All |
| Emby library in feed-group mode | every feed-group pill | New, All |
| Shows, Movies and other Emby libraries, Home, Audiobooks | none | every pill |

A pill names a collection when it narrows the list to one content set the Service holds (a group folder, a show, a subscription); Latest, filters, and letter or surname buckets are views, not sets. A collection pill toggles; a single pill (Latest, filters, letter buckets) clears the set and selects alone. The core keeps at least one pill selected and gives the clear control the first selected pill in pill order. The list is the union de-duplicated by item id, in the destination's existing sort.

**Who holds the set, and how it loads.** Where the `App` holds the selected collection today, the `App` keeps holding it, and the extra collections join it there; the projection (design D2) reads the set from the `App`, so no Surface state mirrors a value the `App` owns. For Music, the first selected group stays the group level's resting cursor in `nav_stack`, and a group switch keeps its path through `App::switch_music_group`. The `App` gains, per Grouped Music library, the extra selected group ids in pill order and one loaded album level per extra group, fetched with the same group-level fetch and the same page-to-completion rule (`maybe_fetch_next_page_sized`) as the first. Removing a group drops its level. Removing the first group makes the next selected group the first: its level replaces the album level in `nav_stack` without a re-fetch. The TUI never adds an extra group, so its `nav_stack` and fetches do not change. An Emby library in feed-group mode follows the same rule from `feed_home_video_selected_group_index` (unit 9). Podcasts keep each show's episodes for the session, so the union reads those cached lists (unit 12). Unit 13 reads the Feeds loader before it plans its union. Where a destination's pill selection is component state today (Podcasts' `pill`), `SelectorSurface` holds the set. `SelectorSurface` always holds the focused pill and pill focus. The TUI adapter never toggles; it selects one pill as today, so its set always has one member.

### D6. The extra pills persist in an additive launch-state field

The `tui-launch-state` main spec persists one pill scope and bans multi-selection, so this change amends it (delta `specs/tui-launch-state/spec.md`). Two destinations persist a live pill today: a Grouped Music library (its selected group) and an Audiobookshelf book library (its selected bucket); every other destination with a Latest pill restores Latest. The shared builder keeps both. The bucket stays single-select, so only Music's extra groups need a new field: `TuiLaunchState` gains `#[serde(default, skip_serializing_if = "Vec::is_empty")] extra_music_groups: Vec<String>` (the group content ids after the first, in pill order). `selector` keeps the first selected group.

The builder writes `item: None`, as every owner's `launch_snapshot` does today (`music_content/owner.rs:148` and siblings), so the TUI snapshot stays byte-identical and the field stays as it is. The user chose one shared file: the GUI Client writes the same snapshot at its orderly exit, and the last completed exit of either Client sets the next launch of both (the existing two-TUI rule; delta `tui-launch-state` "Launch state is written only at orderly TUI exit"). After the port, one snapshot builder reads `App::tab`, the destination's `SelectorSurface` (the selector set with its stable `SelectorIdentity` values), and the `FocusStack` (Panel focus); `Model::launch_state_snapshot` calls it in place of reading the component, so the TUI's snapshot stays byte-identical, and the GUI core thread calls it at its exit boundary and saves through `mbv_config::save_tui_launch_state` before `client_exit_teardown`. The GUI saves only at orderly exit, never while open. The builder writes the extra groups only when Music is the selected tab (the snapshot holds no state for unselected tabs), from the `App`'s extra Music groups (design D5), which the TUI never fills, so a TUI snapshot carries none.

**The restore becomes one shared step.** The `App` already settles the tab (`LaunchRestore::TabSettled`). The pill and Panel-focus half (`Model::reanchor_pending_launch_destination`) reads the TuiRealm `LibraryPanel` today; after the port it reads the destination's `DestinationSurface` and the `App`, so it moves to a shared `App` step that both Clients run after the selected destination's content lands: it resolves the selector, applies it, then calls `App::set_panel_focus` with the saved Panel focus, and the focus stack follows (design D1). The TUI's step output stays byte-identical. The GUI then runs one GUI-only step: it applies `extra_music_groups` to the `App`'s Music group set, after the shared step resolved the first group. The TUI has no such step, so it restores the first group only. A saved extra group that the library no longer has is dropped, not replaced: the first-guaranteed-pill fallback applies only to the first group.

**A saved tab that the GUI does not present.** The `App` settles the saved tab whenever that library exists (`select_tab`, `src/app/dispatch/library/cw_library_tab.rs:141-150`), so a snapshot that the TUI wrote on Shows restores Shows in the GUI while Phase 1 presents only Music. While the frame presents a subset of the destinations, a GUI-only step runs after the `App` settles the tab: if `App::tab` is not a presented destination, it calls `App::set_library_tab` with the first presented one, before the shared restore step, and the shared step then restores that destination's pill and the saved Panel focus. The GUI's exit snapshot then writes the destination it showed, by the last-exit rule. When all seven destinations are presented, the step has nothing to do and is deleted with the last port (unit 15). `CoreThread::new` no longer hardcodes Queue focus: before restore, the stack follows `App::effective_panel_focus()`, as in the TUI. In the session, each destination keeps its set because owners stay mounted.

The main spec's "SHALL NOT record the selected library item" already disagrees with the struct's `item` field; that drift predates this change and the delta does not touch it.

### D7. The letter rail reads the list's sort names

The frame carries the letters that have rows. A press emits a jump `Msg`; the core moves the cursor to the first row whose sort name starts with the letter (the sort-name rule the destination already sorts with) and re-anchors the viewport. The rail follows the list's current sort, not the destination: it shows only while the list is sorted by name and the list has the `/` inline filter, which is the rail's keyboard path (Music artists, Shows series, and an Emby library while its sort is by name). Audiobooks has no inline filter, so its books show no rail and never on a Latest view or a date-sorted list (Home, Feeds, Podcast episodes, an Emby library sorted by date).

### D8. `Ctrl+K` binds Search in the GUI-only key context

`Ctrl+K` binds `search_open` in the GUI-only key context that already holds `z`, `q`, and `c`. The TUI's defaults do not change. The Search results paint in the Music list-row look.

**Open, focus, activate, dismiss.** `open_search_sidebar` only arms a sidebar-open request for the TUI shell to mount (`src/app/dispatch/library/search.rs:27-30`). The GUI core thread takes that request for Search after each dispatch: it opens the `SearchSurface`, pushes it on its `FocusStack` so the query field holds focus, and the frame carries Search as open. `SearchActivate` gets a routed arm that runs `App::activate_search_result` and closes Search; `DismissSearch` gets a routed arm whose follow-up closes the `SearchSurface` and pops it from the `FocusStack`, as the TUI shell's `navigation.rs:124-132` arms do.

The same GUI-only context binds `{` and `}` to move the focused pill back and forward without changing the selection, Space and Alt+Space to toggle and solo the focused pill (design D5), and Backspace to clear the selection. `[` and `]` keep the TUI effect in both Clients: they move the focused pill and select it alone. The focused pill is `SelectorSurface` state; the TUI adapter keeps it equal to the selected pill.

**Gate and precedence.** Space is `toggle_play_pause`'s default chord, and the media list's Visual selection also claims it; `KeyPolicyGate::GuiClient` (`src/app/input/key_policy.rs:305-309`) tests the Client kind and excludes a blocking overlay and text entry, but it does not test Panel focus or pill focus. So the selector chords get their own gates. `{` and `}` need only Library Panel focus, and they give the selector *pill focus*. Space, Alt+Space, and Backspace need Library Panel focus **and** pill focus. `{` or `}` gives the selector pill focus (the focused pill paints its focus ring). A pointer press or Alt-press on a pill also gives the selector pill focus and makes that pill the focused pill, as a press on a button focuses it, so a following Space toggles that pill. Any other Library navigation key, a press outside the pill row, or Esc returns pill focus to the list. While the selector holds pill focus, Space, Alt+Space, and Backspace resolve on the selector first, ahead of `toggle_play_pause` and the Visual-selection candidate; at every other time Space keeps its existing meaning in both panels. Pill focus is `SelectorSurface` state. The key-policy snapshot gets it from the focused `GuiSurfaceLeaf`, through a new `pill_focus_active` method beside `visual_selection_active` (`src/app/input/gui.rs:53`); the TUI snapshot sets it false. `[` and `]` are Library navigation keys, so after either the selector does not hold pill focus and a following Space plays or pauses. *Pill focus* names only this selector mode; the pill that the mode acts on is the *focused pill*, which exists in both modes. Backspace runs the clear control (only the first selected pill in pill order stays), so clear has a keyboard path. The five chords stay canvas-fixed literals, so the keybind recipe in `docs/recipes.md` does not apply. They are not command entries like `z`, `q`, and `c`: each of those has a `command_for_policy` arm (`src/app/input/key_policy/commands.rs:47-56`), and a router `Command` never reaches the leaf. The five are pass-through policy entries: non-blocking, with no `command_for_policy` arm, so the router returns `FallThrough` for them (`src/app/input/router.rs:115-125`) and the Library leaf runs them on its `SelectorSurface`. They sit in the GUI-only block (`key_policy.rs:416-455`), ahead of `toggle_play_pause` (`:594`) and the blocking `alt_swallow` (`:719-725`, which matches every Alt chord, `:233`), so that with their gates open, Space and Alt+Space reach the leaf and not those entries.

The Phase 1 gate's live test checks Alt+Space under GNOME on Wayland (the compositor can take Alt+Space for its window menu) and the `{`/`}` spelling with Shift on the user's layout.

### D9. The Status bar moves to the Library column

The shared Status bar projection carries the prefix state and the toast (`mbv_surfaces::status_bar`, `GuiStatusBar`). When the Library panel shows, those two paint in a Library Status bar under the Library column; when only the Queue panel shows, the Queue footer paints them as today.

The Library Status bar adds two GUI-only items that the canvas Library artboard shows (`canvas/Library.dc.html`, the bottom bar) and no Status bar carries today:

- **Key hints** (left): the main actions of the focused Library surface (filter, play, play next, add to queue, Panel focus, tab jump). The frame carries each hint as an action id plus the chord that runs it in the GUI: the configured chord for a registry action that `[keys]` binds (Panel focus, tab jump, search), and the fixed key for the rest: `/` and Enter are the owners' fixed keys, and `n` and `a` are the GUI-only Library chords of design D16. The Hero action hints follow the same rule. Prefix or toast replaces the hints while active.
- **Location** (right): the destination name, the selected pill names, and the selected item title, each a fact the Library frame already carries. The front end joins them.

The TUI Status bar's other items (volume and mute pills, the Visual-mode indicator, the queue-source link, username, and Service glyphs) do not paint in the GUI: the canvas shows none of them, and the Queue footer already paints the queue source and the owner marker.

### D10. The canvas look comes through GUI-local tokens

The Library paints the canvas values through the GUI-local `--canvas-*` tokens in `crates/mbv-gui/ui/src/app.css`, with new tokens for the Library-only values. No `mbv-theme` slot changes.

### D11. The Hero's more-actions control opens the Library item context menu

The canvas Hero has *More album actions* and *Shuffle artist* (`canvas/Library.dc.html:99,114`). Shuffle artist runs the TUI owner's existing shuffle action (Ctrl+S on an artist row, `MusicTreeAction::Shuffle`), and its hint shows Ctrl+S. More actions opens the TUI's Library item context menu for the Hero's item: the GUI ports it as an overlay, with the menu state in the core (the same overlay path as the queue row menu: `GuiOverlayFrame` gains a Library item menu section, and the GUI's documented no-op for `ContextMenuTargets::Emby(_)` in `src/app/input/gui.rs:334` becomes a routed target). It paints in the row-menu look and opens from the keyboard by the TUI's context-menu chord on the selected item.

### D12. Letter headings are non-selectable rows at the fixed row height

The canvas list interleaves 24 px letter headings with 30 px rows. A fixed row height is required so that capacity is a whole number of rows, so a heading is a non-selectable row of the list flow at the same row height. `ListCapacity` counts every row, headings included; the cursor and the paging stride skip headings, as they skip any non-selectable row. The heading paints at the canvas heading's type and colour inside the taller row.

### D13. The service bootstrap becomes a shared Client step

The TUI-only bootstrap steps move into one `App` step, `App::start_client_services`, that both Clients run once after the attach: the Emby startup worker (the full library bootstrap), the Audiobookshelf startup worker, `start_feed_fetch`, and capability registration. `Model::spawn_startup_services` calls it in place of its body, at the same point after the first frame, so the TUI's order and timing do not change. The GUI core thread calls it in place of `start_emby_client_fill`; the full Emby startup also installs the client that the session list, cast discovery, and artwork read, so the client-fill exception (add-tauri-gui-client design D9) is retired and `start_emby_client_fill` and its worker are deleted with their tests.

**The GUI keeps its playback-target discovery.** The fill also starts the `/Sessions` fetch and the cast browse that feed the GUI's playback-target chooser (`spawn_sessions_load` and `spawn_cast_discovery`, `src/app/dispatch/session/command.rs:17-20` for a cached client, `emby_service_completion.rs:84-100` on fill completion). `apply_emby_startup` starts neither, and the GUI chooser has no open step that refreshes them (the TUI starts them when its session sidebar opens, `src/app/shell/overlays/sidebars.rs:60-61`). So the GUI core thread starts both loads at the same two points as the fill: right after `start_client_services` when the attach brought a cached Emby client, and in its `drain_startup_workers` host when the drain reports a successful Emby startup. `StartupWorkerDrain` (`src/app/client_drains.rs:77`) gains that fact (`emby_started`); the TUI host ignores it. `apply_emby_startup` does not change, so the TUI's startup does not change.

The completions already drain App-side through `drain_startup_workers` and `drain_lib_events` in the GUI tick host, so `App::libs` and the catalog fill, and `LaunchRestore` settles the tab.

**The library views on a cached-client launch (Phase 1).** On the normal configured launch, the attach brings a cached Emby client (`src/owner_link.rs:100`), so `emby_startup_request` is not armed (`src/app/state/construct/remote.rs:133,191`), no Emby startup worker runs, and `apply_emby_bootstrap` never builds the tabs. On that path only `App::fetch_home` builds them (`get_views_classified`, then `rebuild_library_tabs_from_views` and `start_album_index`, `src/app/dispatch/library/load.rs:365-391`), called from `Model::fetch_home_at_startup` (`src/app/shell/home_content.rs:184`) right after `spawn_startup_services` (`src/app/shell/run.rs:272-274`). So Phase 1 moves the `App` half of `fetch_home_at_startup` into a shared `App::load_home_at_startup() -> Option<HomeContent>`: `fetch_home`, then on success `spawn_home_recently_added(Emby)` and the status clear, and on failure the "Couldn't load home" toast. Both Clients call it right after `start_client_services`. The `Model` keeps only the Home half: it sets `home_content.loading`, assigns the content, or pushes the old content on failure, as today, so the TUI's calls and their order do not change. In Phase 1 the GUI drops the returned content (no Home surface); unit 10 stores it in Home's `DestinationSurface`. `init_idle_feed` is `Model` code for the idle feed; it joins the shared step in unit 10, under the same rule. The startup drain also returns the Home content that `apply_emby_bootstrap` builds (Continue Watching and the other sections, `StartupWorkerDrain::home`); the TUI host assigns it (`src/app/shell/run/drains.rs:19-25`), and the GUI host drops it today (`crates/mbv-gui/src/core_thread/tick_host.rs:18-22`). In unit 10 the GUI host stores it in Home's `DestinationSurface`, from which the Home projection builds its slots.

*Alternative:* call the TUI steps from `mbv-gui`. Rejected: they are `Model` methods, and the guide forbids a copy in `mbv-gui`.

### D14. Library request dispatch becomes a shared App step

Each Library `ShellRequest` handler splits on the seam it already has: the `App` effect, and the TuiRealm step that re-pushes or re-anchors the mounted owner. The effect half moves to an `App` method (`App::handle_library_request`, in `src/app/dispatch/library/`) that both Clients call. It returns a `LibraryFollowUp` value (re-anchor the destination to a target or to the level start, arm a track-focus request, open the Hero overlay, select a track when its rows land), and each Client applies it to its own surface: the TUI to its mounted owner, exactly as today, and the GUI to its `DestinationSurface`. The GUI's `DestinationSurface` belongs to `CoreThread`, not to the `App`, so the `App` cannot apply it: `App::handle_gui_surface_msg` and `handle_gui_queue_shell_request` (`src/app/input/gui.rs:256,305`) return `Option<LibraryFollowUp>`, the GUI key and pointer entry points return it to `CoreThread`, and `CoreThread` applies it to the Library `DestinationSurface` that it owns.

**Common navigation routes too.** `TabSelect` is a Library request: its effect half (`App::set_library_tab`, `src/app/shell/messages/navigation.rs:72-76`) moves into `App::handle_library_request`, and its follow-up closes the active destination's filter draft and clears the Client's Visual selection, as the TUI shell does. The GUI's Search requests (`SearchActivate`, `DismissSearch`) get routed arms in unit 14 (design D8). The pending values that `Model` holds today (`pending_music_reanchor`, `music_track_focus_request`, `pending_music_track_selection`) move to the `DestinationSurface`, since both Clients need them. `handle_gui_queue_shell_request` gains a routed arm per Library request a ported surface emits, in place of the catch-all; a request from a destination the GUI does not yet present stays in the logged arm. Each unit moves only its own destination's handlers: Phase 1 moves the Music requests, `TabSelect`, `LibraryPanelFocus`, `LibraryViewportReach`, `LibraryScroll`, `OpenInlineSearch`, and `MusicRowContextMenu`. The TUI's tick and message tests are the proof and pass unedited.

### D15. Library focus takes the Library keys from the existing GUI chords

Four existing GUI-only chords use keys that the Library uses: `/` opens the Queue filter (`gui_queue_filter_open`, `key_policy.rs:244`), `[` and `]` run `seek_back_10` and `seek_forward_30` (`crates/mbv-keybinds/src/registry.rs:384-399`), and `a` runs `open_audio_popover` (`registry.rs:408-416`, `key_policy.rs:498-503`). Their `GuiClient` gate (`key_policy.rs:305-309`) does not test Panel focus, and a router `Command` never reaches the leaf (`src/app/input/gui.rs:167`). So the Library would never see these keys.

The rule: while Library has Panel focus, a GUI-only entry whose resolved chord is one of the Library's fixed keys (`/`, `[`, `]`, and the D16 chords `n` and `a`) does not match, and the key falls through to the Library leaf. With Queue focus, these entries keep their effect: `/` opens the Queue filter, `[`/`]` seek, and `a` opens the audio popover. So the audio chip's `a` works only with Queue focus; the chip's press works from both. The test is on the chord, not the action, so a seek that the user rebinds to a key outside that set keeps working with Library focus. A new gate, `KeyPolicyGate::GuiOutsideLibraryKeys`, holds the rule; the four entries move to it. The key-policy snapshot gets Library focus from `App::effective_panel_focus()` (`library_focused`); the TUI snapshot sets it false, so the TUI resolution does not change. While the Library filter draft is open, the snapshot sets `text_entry_focused`, so the GUI-only chords stay out of the typed text, as for the Queue filter.

### D16. Library play next and the GUI action chords are new GUI behaviour

The TUI has no Library play-next action: Music runs play, add to queue, and shuffle with Ctrl+P, Ctrl+A, and Ctrl+S (`music_content/owner.rs:503-530`), and `App::play_queue_item_next` (`src/app/dispatch/queue.rs:221-249`) moves a slot that is already in the queue. The canvas shows *Play next* with `n` and *Add to queue* with `a` (`canvas/Library.dc.html:112-113,148`). So:

- **Existing TUI actions, ported as they are:** Enter and Ctrl+P (play), Ctrl+A (add to queue, `App::enqueue_lib_item`), Ctrl+S (shuffle), `/` (filter), `[`/`]` (pill). The TUI keeps them unchanged, and the GUI gets them through the leaf.
- **New GUI action, play next:** a new `ShellRequest::EmbyLibraryPlayNext { item }` and a shared `App::play_lib_item_next(lib_idx, item)`. It resolves the item through the same route and admission checks as `enqueue_lib_item` (folder expansion, playability, route conflict), then sends the owner's answered Append with `before` set to the slot right after the active slot (`QueueOp::Append { items, before }`, `crates/mbv-remote-player/src/lib.rs:32-35`). When the active slot is the last one, or there is no active slot, it sends `before: None` (append). It inserts Library content; it never moves a slot. The TUI has no producer; its `ShellRequest` dispatch gets an arm that calls the same method, so the match stays exhaustive.
- **New GUI chords:** `n` (play next) and `a` (add to queue, the Ctrl+A effect) are canvas-fixed literals. They need no policy entry: `n` has no GUI or TUI binding, and with Library focus `a` falls through by D15, so both reach the Library leaf. The GUI Library leaf handles them before it delegates to the shared `DestinationSurface::key`, so the TUI never sees them. They emit on the Library item under the cursor: the selected list item, or the Workspace cursor row when the Workspace has focus. The Hero controls and the Workspace hover controls send the same requests. The TUI defaults do not change.

## Risks / Trade-offs

- [The shared bootstrap and the request dispatch move touch TUI startup and message code] → Each move keeps the TUI call order; the TUI startup, tick, and message tests are the proof and pass unedited.
- [The seven owner ports are large and touch TUI code] → Each port is behaviour-preserving and its proof is the existing TUI test suite, unchanged. Music lands first, so the port pattern is reviewed before it repeats.
- [A union of collections makes one fetch per selected collection] → The owner reuses the existing fetch and cache per collection; a selected collection that fails to load keeps the others and shows the TUI's failure text for that collection.
- [An older `mbv` binary may read a launch state with `extra_music_groups`] → `TuiLaunchState` has no `deny_unknown_fields`, so serde ignores the field and the older binary restores the first pill.
- [The breakpoint thresholds may feel wrong live] → They are constants beside the front end's panel-state constants; the Music gate's live test checks them.

## Migration Plan

One change, two phases with an acceptance gate:

1. **Phase 1 — Music from end to end.** The shared service bootstrap (design D13), the shared Music request dispatch (design D14), the shared launch restore (design D6), the Library Surface state and the Music port, the frame section, regions, leaf, and core wiring, the window arrangement (breakpoints, Panel focus, Hero overlay), the top bar tabs (only the destinations the frame can project; the other tabs are absent until their unit lands, under the no-stub rule), the Status bar move, the Music slot painters, Music's Inline Search filter, the Hero's shuffle and more-actions menu, multi-select pills with persistence, and the letter rail.
2. **Gate.** A `/code-review` round over Phase 1 and a user live-test round. Phase 2 starts only after the user accepts Phase 1. The gate is not a task.
3. **Phase 2 — the other destinations and Search.** Shows, Movies and other Emby libraries, Home, Audiobooks, Podcasts, Feeds, then global Search. Each destination is one port plus its slot content; the painters from Phase 1 do not change except for slot variants that Music does not use (landscape and portrait art, the Workspace selector, no Hero).

Rollback is a per-unit revert. No Owner-side or stored-state change exists apart from the additive launch-state field.
